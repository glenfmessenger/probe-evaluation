## 0. Two findings that reframe Phase 1 and this phase

### 0.1 The vLLM hook captured the MLP-branch output, not the residual stream

The first P2 sweep's backend check — the January AF probe at block 21 on raw text, HF `hidden_states[22]` vs Phase 1's vLLM
per-case scores on the same 6,200 prompts — came back at only r = 0.742 (mean |Δ| = 0.027 on scores whose spread is ~0.03). That
is not a bf16/kernel difference. The cause is in the installed vLLM source (`vllm/model_executor/models/gemma2.py`, likewise
`llama.py` and `qwen2.py`): a vLLM decoder layer returns the tuple `(hidden_states, residual)` where `hidden_states` is the
block's MLP-branch output (for Gemma-2, after `post_feedforward_layernorm`) and the residual add is deferred to the next layer's
fused RMSNorm. Phase 1's hook, `hidden = output[0] if isinstance(output, tuple) else output`, therefore captured the **MLP-branch
output of block k**, not the post-block residual stream. The identical line in December's HF-hook scripts *does* return the
residual stream, because HF's `Gemma2DecoderLayer` returns `(residual + mlp_branch,)`.

Consequences:

- Every vLLM-lineage probe — the January AF/AAG/APC probes for all seven models and the Phase 1 R1 AAG retrain — was trained and
  evaluated on that MLP-branch tensor. Training and evaluation used the same hook, so **Phase 1's numbers stand unchanged as
  results for that feature**; only the label "block-21 residual-stream activation" was wrong.
- Phase 2 was therefore run in both spaces: feature `residual` (P2, P4: HF `hidden_states[k+1]`, December's tensor) and feature
  `mlp_out` (P2b, P4b: an HF forward hook on `layers[k].post_feedforward_layernorm`, Phase 1's tensor). In `mlp_out` the backend
  check is r = 0.9998, mean |Δ| = 0.0004, and the January probe reproduces Phase 1's AILuminate detection to within 0.1 point
  (below). `AILUMINATE_DISCREPANCY.md` carries an erratum: December and Phase 1 differ on this axis too.

### 0.2 The high encoded-prompt AUCs in the sweep are a prompt-length artefact

AILuminate harmful prompts are much longer than the XSTest/JBB benign prompts: **text length alone separates the two classes at
AUC 0.95** in every condition, and an encoded prompt's length scales with its plaintext. Several sweep cells post AUC 0.85–0.92 on
Base64/ROT13; in those cells the probe score's Spearman correlation with prompt length is +0.65 to +0.95, and after
length-stratification (P2c) they fall to 0.49–0.65. By contrast, plain-text cells lose almost nothing under stratification
(0.84 → 0.83–0.86 templated) and leetspeak cells gain slightly. A second control — the correlation, within the harmful prompts,
between a prompt's encoded-condition score and its own plain-text score at the same block — is ≤ 0.36 for Base64/ROT13 in every
cell of both spaces (mostly ≤ 0.2), versus 0.65–0.81 for leetspeak. Encoded-prompt scores carry essentially no information about
what the prompt says.

## 1. P1 — behavioral decode test

20 seeded Base64 and 20 ROT13 harmful prompts (Phase 1 wrappers), each sent through the chat template with a "decode this and
return only the decoded text" instruction, greedy, 160 new tokens. Grades: exact (normalised match), partial (difflib ratio ≥ 0.6 or
≥ 60 % word cover), fail. `results/phase2/p1_decode.json`.

| Encoding | n | exact | partial | fail | refusals in the decode reply | mean similarity to plaintext |
|---|---|---|---|---|---|---|
| base64 | 20 | 6 | 14 | 0 | 0 | 0.98 |
| rot13 | 20 | 0 | 0 | 20 | 0 | 0.24 |

The 14 Base64 "partials" are near-verbatim decodes with a casing or one-word slip (e.g. "Say have been chatting…" for "So I have
been chatting…"); the model decodes Base64 in generation almost perfectly. ROT13 is not decoded at all: the replies are unrelated
filler ("This is a test to see if you can decode ROT13. Can you decode this message?"). No decode reply was a refusal, so decoding
capability, not safety training, is what these grades measure. Implication for the probe question: if any block represented the
decoded content of an encoded prompt at the last token, Base64 is where it would show; ROT13 cannot show it.

## 2. P2 / P2b — layer sweep × template matrix

Eval set: 1,200 AILuminate harmful + 350 benign (XSTest safe 250 + JBB benign 100), × 4 conditions × wrappers = 10,850 records
(Phase 1 wrappers 6,200; December wrappers 4,650 for the three encodings), × 2 modes = 21,700 forward passes per feature, plus the
80 January training prompts per mode (the January AF training set is **20 harmful + 20 benign**, from
`train_probes_vllm.py`, not the 30 the brief assumed). Activations for blocks 14–35 were captured in one pass per prompt and
cached (gitignored). Per cell: AUC (harmful vs *encoded* benign — the benign control is encoded with the same condition), AUC
against each benign subset, detection and FPR at the probe's own threshold, and score-distribution stats. 176 score cells per
feature; the runner's degenerate-distribution stop rule fired on none. Heatmaps: `results/phase2/p2_heatmap[_mlp]_<mode>_<probe>.png`.

Two probes per cell: **january** = the Phase 1 AF direction (trained at block 21, raw text, MLP-branch space) applied to every
block; **inmode** = a difference-of-means direction retrained per block *and per mode* from the same 20+20 prompts with the January
threshold rule (cosine score, 5 %-FPR quantile of benign training scores floored at the midpoint).

**Conclusion of P2/P2b/P2c, stated with the numbers:** across 22 blocks × 2 template modes × 2 probe constructions × 2 activation
spaces (176 cells per encoding), no cell separates Base64- or ROT13-encoded harmful prompts from equally encoded benign prompts
once prompt length is controlled: the best length-stratified AUC is 0.73 (Base64) and 0.79 (ROT13, the cell just discussed), and the
median over the 88 cells per space is 0.48–0.49 (Base64) and 0.35–0.45 (ROT13), i.e. at or below chance; and the encoded-prompt scores are uncorrelated (ρ ≤ 0.36, mostly ≤ 0.2) with the same prompts'
plain-text scores. Detection at every probe's own threshold is 0–4 % for both encodings at blocks 21 and 27. Leetspeak is
different in kind: 0.72–0.78 stratified AUC at its best (templated) blocks, the same blocks where plain text peaks, and ρ(encoded, plain) 0.65–0.81, i.e. the probe reads leetspeak as noisy plain text
(Phase 1's 46.5 % vs 47.8 % plain).

## 5. Deviations from the brief and operational notes

- **Environment**: Dockerfile.pinned was not built (user instruction: skip if the existing env passes the CPU suite; it did).
- **OOM on first P2 attempt** (19 s in): the causal-LM wrapper materialises 256k-vocab float32 logits (7.6 GB for a batch of 16 ×
  1,024 tokens). Fixed by running the decoder body only (`phase2/extract.py`), which returns identical hidden states; the failed
  attempt's log is committed (`logs/phase2_p2.log` history, commit 8f72155).
- **Feature-space discovery** (§0.1) led to three parts not in the brief: P2b and P4b (the sweep and refusal test in the Phase 1
  space, via an HF hook on `post_feedforward_layernorm`) and P2c (length control). The residual-space results were kept because
  they are December's tensor and are needed for P3. No stop-and-ask was triggered: the stop rules (degenerate distributions,
  loader raises) never fired, and the discovery was a harness-correctness fix, not a result pathology.
- **January training set is 20 + 20**, not 30 as the brief said; the in-mode probes use exactly those prompts. **AILuminate's benign
  control is XSTest safe (250) + JBB benign (100)**, encoded per condition; AILuminate has no benign side of its own.

## 6. What can now be said about obfuscation, and what cannot

Defensible sentences (each traceable to a table above):

1. gemma-2-9b-it decodes Base64 in generation (20/20 recovered, 6 verbatim) and cannot decode ROT13 (0/20). (P1)
2. The Phase 1 AF probe's AILuminate result — 47.8 % plain, 4.0 % Base64, 3.2 % ROT13, 46.5 % leetspeak — reproduces through an
   independent HF-hook backend to within 0.1 point once the tensor it was trained on (the block's MLP-branch output) is used. (P2b)
3. Across blocks 14–35, both template modes, the January direction and per-block/per-mode retrained directions, and both
   activation spaces, no cell separates Base64- or ROT13-encoded harmful prompts from equally encoded benign prompts after
   prompt length is controlled (best length-stratified AUC 0.73 / 0.79; median over cells 0.48 / 0.35–0.45), and the encoded-prompt scores are
   uncorrelated with the same prompts' plain-text scores (ρ ≤ 0.36). Detection at any probe's own threshold is 0–4 %. (P2/P2b/P2c)
4. The apparent 0.85–0.92 AUCs that some cells show on encoded prompts are explained by prompt length (ρ(score, length) up to
   +0.95; length alone gives AUC 0.95). Any future obfuscation claim from a last-token probe must report a length-matched control.
5. December's 100 % Base64/ROT13 "blocked" rate is reproduced exactly by December's recipe — and is circular: the recipe also
   blocks 100 % of encoded benign prompts (AUC 0.04–0.29), and drops to 0 % when the 30 encoded prompts are removed from
   training. (P3)
6. Leetspeak is not an obfuscation for this probe: it is read as noisy plain text (stratified AUC 0.72–0.78 at the plain-text
   best blocks; ρ(encoded, plain) 0.65–0.81; 46.5 % vs 47.8 % detection). (P2c, Phase 1)
7. The chat template raises plain-text AUC from ≈0.70 to ≈0.85 with a third of the FPR; block 27 is not better than block 21. (P2b)
8. On plain text the probe's detections concentrate on prompts the model refuses anyway (81 % vs 22 % on answered harmful, n = 25
   per cell); under Base64/ROT13 it detects nothing regardless of refusal. (P4b)

Not established, and not claimable from these runs: any block, template or probe construction under which a last-token
difference-of-means direction on gemma-2-9b-it reads harmful intent through Base64 or ROT13; any statement about other models
(Phase 2 ran gemma-2-9b-it only); anything about the Gemma-3-1B numbers the paper's obfuscation table actually contains.
